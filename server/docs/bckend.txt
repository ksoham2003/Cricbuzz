1. Project Overview
1.1 Project Name & Purpose
The project is the Cricbuzz - Backend - a production-grade RESTful API server that powers a full-featured cricket
management and live-scoring platform. It exposes two distinct surfaces:
• Admin API - authenticated, role-protected endpoints consumed by an operator dashboard (super-admins,
admins, scorers) to manage series, teams, players, squads, matches, scores, and commentary.
• Public API - unauthenticated, heavily-cached GET endpoints consumed by fan-facing web/mobile clients for
home feeds, live match centres, scorecards, commentary, series standings, and global search.
1.2 Core Features
Auth & RBAC JWT-based authentication with three roles: SUPER_ADMIN, ADMIN,
SCORER. Every admin endpoint enforces role membership.
Series Management CRUD for cricket series with season uniqueness, soft-delete protection
(cannot delete if matches exist).
Team & Squad Team CRUD with logo/colour, squad management (add/remove players with
idempotency via $addToSet / $pull).
Player Registry Global player catalogue with batting/bowling styles, soft-delete.
Match Lifecycle Strict state-machine: UPCOMING → TOSS_COMPLETED →
PLAYING_XI_SELECTED → LIVE → INNINGS_BREAK → COMPLETED.
Playing XI Selection Validates exactly 11 players, no duplicates, one captain, one wicket-keeper, all
from registered squad.
Live Scoring Real-time score creation/update during LIVE matches, with run-rate and target
tracking.
Commentary Ball-by-ball commentary (NORMAL/FOUR/SIX/WICKET/MILESTONE) with
paginated public feed.
Real-Time Push Socket.IO rooms per match. Score, commentary, toss, playing-XI, start, and
complete events broadcast instantly.
Points Table Derived on-the-fly from completed matches: played/won/lost/points sorted by
points desc, won desc.
Global Search Cross-entity regex search across players, teams, and series (min 2 chars, max
10 results per entity).
Response Cache In-memory TTL cache for all public GET routes. TTLs: 5–60 seconds
depending on data volatility.
Seeder One-command database seeder with realistic BGT-2026 fixture, players, and
live commentary samples.
Docker Production-ready Dockerfile + docker-compose with MongoDB 7,
healthchecks, and named volumes.

1.4 High-Level Architecture
The backend follows a modular monolith architecture. Each domain (series, team, player, match, score, commentary
…) is self-contained in its own folder under src/modules/. Modules expose a consistent four-layer stack:
Route Declares HTTP verb + path, wires middleware (auth, validate) to controller handler
Controller
Thin adapter - calls service, serialises response to JSON, delegates errors via
asyncHandler
Service All business logic, cross-module coordination, error throwing, socket emission
Repository Pure DB calls (Mongoose) - zero business logic, zero HTTP knowledge
A public user/ sub-tree inside modules mirrors the admin modules but is read-only, unauthenticated, and caches
responses. The two trees share the same Mongoose models - there is no data duplication.
Communication between modules happens through direct require() imports of repository/service files - no IoC
container at runtime, though a static container.js registers all singletons for documentation purposes.

3. Folder-by-Folder Analysis
3.1 server/ (root)
The root of the deployable unit. Contains Docker configuration, npm manifest, and the seed script. Acts as the container
for the entire Node.js application.
Dockerfile
Builds a production node:20-alpine image, installs npm deps, exposes port 3000, includes HTTP healthcheck.
docker-compose.yml
Defines two services: app (Express) and mongodb (Mongo 7). App waits for MongoDB healthcheck. Named volumes
persist data across restarts.
.dockerignore
Excludes node_modules and .env from Docker context to keep image small.
package.json
Declares all 10 runtime deps, three npm scripts (dev/start/seed). No devDependencies (nodemon expected globally or
in Docker layer).
3.2 src/config/
Application bootstrap configuration. Two files, both required before routes load.
db.js
Async function connectDB() uses mongoose.connect(). Falls back to localhost/cricbuzz_backend if MONGODB_URI
env is absent. Called in server.js before listen().
container.js
Static service locator that eagerly requires every repository and service. Not used at runtime for injection - serves as a
central manifest and documentation aid.
3.3 src/modules/auth/
Handles user registration and login. No protected routes - these are the entry points for all credential flows.
auth.service.js
signToken() builds a 7-day JWT (id, role, email). register() checks email uniqueness, bcrypt-hashes password, creates
user. login() compares hash, returns token.
auth.validator.js
Zod: registerSchema requires name, email, password (min 6), optional role enum. loginSchema requires email +
password.
auth.route.js
POST /api/auth/register and POST /api/auth/login. Both pass through validateRequest middleware before controller.

4. File-by-File Analysis (Key Files)
src/server.js - Application Entry Point
This is the first file Node.js executes (node ./src/server.js). It bootstraps the entire process.
Imports http (native), socket.io Server, express app, connectDB, initSocket
Creates http.Server wrapping the Express app, then passes it to new Server() for
Socket.IO
Startup sequence 1. connectDB() → 2. server.listen(PORT) - server only starts after DB is
ready
Error handling DB connection failure calls process.exit(1) - container restart policy
handles recovery
Socket.IO CORS Reads CORS_ORIGIN env; defaults to * (should be restricted in
production)
src/app.js - Express Application Factory
Creates and configures the Express application. All route mounting happens here. Does NOT start the HTTP server
(that is server.js's job).
Global middleware cors() (no options = allow all origins), express.json() with 5 MB body limit
Health endpoint GET /health - returns 200 JSON, used by Docker healthcheck and load
balancers
Route ordering Public user routes are mounted BEFORE admin routes on the same path
prefix. Express's first-match-wins ensures public GETs are served by the
cached, unauthenticated handlers. Admin POST/PATCH/DELETE fall
through to the second mount.
Error middleware notFound (404) and errorHandler (global) are registered last in the chain
Cache middleware responseCache(ttl) is applied per-router at mount time, not globally
src/shared/middleware/auth.js
authenticate() Reads Authorization: Bearer header. jwt.verify() with JWT_SECRET env.
Attaches decoded payload to req.user. Throws UnauthorizedError on
missing or invalid token.
authorize(...roles) Higher-order function returning middleware. Checks req.user.role is in the
allowed roles array. Throws ForbiddenError if not.
Security note JWT_SECRET falls back to 'change-this-secret' - MUST be overridden in
production via environment variable.
src/shared/middleware/validateRequest.js
Implements schema-first request validation using Zod. Every route that writes data passes through this middleware.
Input A Zod schema that describes { body, params, query }

src/modules/user/cache/responseCache.js
Type In-process (non-distributed) Map-based TTL cache
Key req.originalUrl - full URL including query string
Stores { status, body, expiresAt } per URL
Bypass Non-GET requests skip cache entirely
Invalidation Pure TTL - no manual invalidation on writes. Score/commentary updates
via Socket.IO compensate.
Limitation Cache is per-process. Horizontal scaling (multiple instances) breaks cache
consistency - requires Redis migration.
TTL values 10s: home, matches | 5s: commentary | 30s: search, points-table | 60s:
series, teams, players
src/modules/user/points-table/pointsTable.service.js
Derives the points table entirely from match results - no dedicated collection. Algorithm:
• Fetch all COMPLETED matches for the series (populated with team/winner refs)
• Use a Map keyed by team ObjectId string to accumulate stats
• For each match: increment played for both teams; increment won (+2 points) for winner, lost for loser
• Sort by points desc, then won desc
This approach is correct and efficient for typical tournament sizes (< a few hundred matches). For very large leagues, a
materialised view would be preferable.

6. Architecture Analysis
6.1 Backend Architecture - Layered Modular Monolith
The codebase implements a clean four-layer architecture within each domain module. Dependency direction is strictly
top-down: Route → Controller → Service → Repository. No layer imports from a layer above it.
Why a modular monolith over microservices? Cricket scoring is stateful and highly relational (match references
series, teams, players, scores, commentary). A monolith avoids distributed transaction complexity while still being
well-structured for a future split if scale demands it.
6.2 Authentication & Authorization Flow
Registration POST /api/auth/register → validate → bcrypt.hash(password, 10) →
User.create() → signToken() → return {token, user}
Login POST /api/auth/login → validate → User.findByEmail() →
bcrypt.compare() → signToken() → return {token, user}
Token structure JWT payload: { id, role, email }. Signed with JWT_SECRET. Expires in
JWT_EXPIRES_IN (default 7d).
Protected request Client sends Authorization: Bearer → authenticate middleware →
jwt.verify() → req.user = payload
Role check authorize(ROLES.ADMIN, ROLES.SUPER_ADMIN) → checks
req.user.role in allowed array
Three roles SUPER_ADMIN: all operations. ADMIN: series/team/squad/player/match
CRUD. SCORER: toss, playing-XI, score, commentary.
6.3 Database Architecture
ODM Mongoose 9 - schema validation, middleware hooks, population, virtuals
Connection Single connection per process managed by Mongoose's connection pool
Soft delete All domain models have isDeleted:Boolean (default false). All repository
queries append {isDeleted:false} filter.
Audit trail createdBy and updatedBy (User ObjectId refs) on every domain model.
Populated via service audit() helpers.
Indexes Match model has 4 compound indexes covering: status+startTime,
seriesId+startTime, team1+startTime, team2+startTime. Score: {matchId,
innings}. Commentary: {matchId, createdAt:-1}.
Embedding vs reference playingXI is embedded in Match (no separate collection) - correct choice
as XI never changes after selection.

Style REST - resource-oriented URLs, HTTP verbs as actions
Versioning None currently - all routes under /api/
Response envelope { success: true/false, data: ... } or { success:false, message:'...', errors:{...} }
Error codes 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409
Conflict, 500 Internal

10. Security Analysis
10.1 Authentication Security
Password hashing bcryptjs with cost factor 10 (~100ms per hash). Timing-safe comparison
via bcrypt.compare().
Token signing HS256 (HMAC-SHA256). Payload: { id, role, email }. Default secret is
INSECURE - must change.
Token lifetime 7 days by default. No refresh token mechanism - compromised tokens
remain valid until expiry.
Token storage Not managed by server - client responsibility. Headers only (Bearer), not
cookies.
10.2 Authorization Security
RBAC enforcement authorize() middleware checks role on every protected route - no capability
escapes to controller layer.
Public routes Intentionally unauthenticated. No write operations exposed publicly.
Scorer scope SCORER can only perform live-match operations (toss, XI, score,
commentary) - cannot modify master data.
10.3 Input Validation
Library Zod 4 - schema-first, safe-parse (no exceptions on invalid input).
Coverage All POST/PATCH bodies validated. Route params validated (objectId
regex). Query params validated where used.
ObjectId validation custom regex /^[0-9a-fA-F]{24}$/ - prevents MongoDB cast errors and
injection attempts.
Regex search input escapeRegex() in search module sanitises user input before building
RegExp - prevents ReDoS.

11. Real-Time Architecture (Socket.IO)
The real-time layer uses Socket.IO 4 in a room-based broadcast pattern. Every match has its own isolated room - fans
subscribed to different matches never receive each other's events.
11.1 Connection Flow
Client connects socket.connect() → Socket.IO handshake (WebSocket upgrade or
long-poll fallback)
Join match Client emits 'join-match' with matchId → server calls
socket.join('match:{matchId}')
Leave match Client emits 'leave-match' with matchId → server calls
socket.leave('match:{matchId}')
Score update Admin scorer updates score → service calls emitToMatch(matchId,
'score.updated', data)
Fan receives All sockets in 'match:{matchId}' room receive 'score.updated' event with
new score payload
11.2 Event Catalogue
Event Trigger Payload
toss.updated Admin Toss recorded - match status, tossWinner, tossDecision
playingXI.updated Admin Playing XI selected - full playingXI embedded in match
match.started Admin Match is now LIVE - status change payload
match.completed Admin Match finished - winner, result, status
score.updated Scorer Innings score changed - full Score document
commentary.created Scorer New ball commentary - Commentary document

12. Caching Architecture
The responseCache middleware provides an in-memory HTTP-layer cache for all public GET routes. It operates by
intercepting res.json() to capture successful responses before they are sent, and returning cached copies on
subsequent requests within the TTL window.
12.1 Cache Configuration by Route
Route Prefix TTL Reason
/api/home 10s Live match status changes frequently
/api/matches (incl. center, scorecard) 10s Live score data
/api/matches/:id/commentary 5s Ball-by-ball updates, shortest TTL
/api/series/:id/points-table 30s Changes only when match completes
/api/search 30s Mostly stable data
/api/series 60s Series rarely change
/api/teams 60s Teams rarely change
/api/players 60s Players rarely change
Design trade-off: Cache staleness is acceptable because real-time Socket.IO events push live updates to subscribed
clients. A fan watching a live match gets immediate score/commentary pushes via WebSocket regardless of the 5-10
second cache window on the REST endpoints.

14.6 Common Debugging Points
JWT errors
Check Authorization header is 'Bearer ' with a space. Verify JWT_SECRET matches between registration and current
run.
Cast errors
MongoDB ObjectId cast error usually means an invalid ID string reached the DB. Wrap route params with
validateRequest(idParamSchema) and use ensureId() in public services.
Match status errors
Follow the state machine strictly. A SCORER trying to add a score before match.status is LIVE will get 400.
Squad validation
createMatch() requires BOTH team squads to have ≥11 players. Seed or manually add players first.
Socket events not received
Ensure client calls socket.emit('join-match', matchId) after connecting. Check matchId matches the match being
updated.
Cache stale data
Restart the server process to clear in-memory cache. Or lower TTL temporarily during development.

15. Project Summary & Recommendations
15.1 Strengths
• Clean modular architecture - each domain is independently understandable and testable
• Strict state-machine for match lifecycle - prevents data corruption from out-of-order operations
• Thorough input validation via Zod on every write endpoint - body, params, and query
• Consistent error hierarchy (AppError subclasses) with correct HTTP status codes
• Real-time Socket.IO integration that correctly fires events only after successful DB writes
• Soft-delete pattern across all models preserves audit history and prevents accidental data loss
• Smart route ordering in app.js allows public and admin routes to share URL prefixes cleanly
• In-memory cache significantly reduces MongoDB load for high-traffic public endpoints
• Production-ready Docker setup with healthchecks and persistent named volumes
• Comprehensive database seeder enables instant development environment setup
15.2 Weaknesses & Technical Debt
No test suite
Zero unit or integration tests. Adding any business logic change carries risk of regression.
In-memory cache
Not horizontally scalable. A second app instance has a cold cache and stale data.
No refresh tokens
7-day JWT with no revocation = security risk on credential compromise.
Insecure defaults
JWT_SECRET and CORS_ORIGIN must be overridden - no startup validation enforces this.
No rate limiting
Auth endpoints are brute-forceable without any throttling.
No pagination on admin list routes
GET /api/series, /api/teams, /api/players, /api/matches return ALL records - will degrade at scale.
No TypeScript
